# ADR-001: Use Terraform for Infrastructure as Code

Status: accepted
Date: 29/10/26

Context: This project requires automatic and repitable deployment of its infrastructure. Deploying every service by hand on the management console leaves no history, cannot be reviewed and is hard to repeat, so an infrastructure as code (IaC) tool is required. A second goal is to learn a tool that carries over to other cloud providers.

Options:
- AWS CDK (generates CloudFormation): Native to AWS and rolls back failed
  deployments automatically; AWS only, and it also requires understanding CloudFormation.
- Terraform: Declarative language (HCL), works across many clouds, widely
  used in cloud and security teams, free to use; I must manage the state file myself, and its license is source-available, not open source.
- Pulumi: Infrastructure written in general-purpose languages such as
  Python or TypeScript, works across clouds; smaller community and fewer examples.

Decision: Use Terraform. Its skills transfer to other clouds, it is widely used in cloud and security roles, and its plan output lets every change be reviewed in a pull request before it is applied. CDK was rejected because it is AWS only; Pulumi mainly because of its smaller community.

Consequences:
- Cost: Terraform is free; the state bucket costs a few cents a month.
- State file risks (loss, corruption, outdated state): keep it in a private
  S3 bucket with versioning and state locking.
- Sensitive data in state: the bucket is private and encrypted, and state
  files are never committed (covered by .gitignore).
- Manual console changes cause drift: all changes go through Terraform, and
  `terraform plan` is run to detect drift.
- License risk: if the license becomes a problem, migrate to OpenTofu, the
  open-source fork.
- Learning curve: deployments will be slower at first. This is accepted as
  part of the project's learning goal.
