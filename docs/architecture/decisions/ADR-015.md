# ADR-015: Pin the OIDC trust to numeric owner and repository IDs

Status: accepted
Date: 2026-11-24
Related: ADR-012 (Identity Center), ADR-014 (Terraform layers)

Context: The pipeline roles trust GitHub's OIDC tokens, and the trust
policy decides which repository may assume them. In my tokens, the `sub`
claim contains the owner and repository names together with their
numeric IDs (`repo:OWNER@OWNER_ID/REPO@REPO_ID:pull_request`). A policy
matching only the names did not match, and the first pipeline run failed
with "Not authorized to perform sts:AssumeRoleWithWebIdentity".

Options:
- Match the names only: it no longer matched my tokens; and names can be
  reused if an account or repository is deleted and recreated.
- Match with a wildcard for the IDs (`StringLike`): works, but would also
  accept a different repository that reuses the same names.
- Pin the exact IDs with `StringEquals`: tied to this repository's
  identity; the IDs must be looked up and kept in variables.

Decision: Pin both numeric IDs with `StringEquals`. The plan role accepts
only `pull_request` from this repository, and the apply role only the
`main` branch. The IDs live in the variables `github_owner_id` and
`github_repository_id`.

Consequences:
- Security: only this specific repository can assume the roles; no
  wildcard is used in either trust policy.
- Maintenance: renaming the repository or owner changes the name part of
  the subject, so the variables must be updated; recreating or
  transferring the repository changes the IDs.
- Values: the IDs are not secrets, but they are kept in
  `terraform.tfvars` (not committed) and found with
  `gh api repos/<owner>/<repo> --jq '.id, .owner.id'`.
- Troubleshooting: when login fails, compare the token's `sub` with the
  trust policy; this is documented in `deploy.md`.
