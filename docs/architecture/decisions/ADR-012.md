# ADR-012: Use IAM Identity Center for human access

Status: accepted
Date: 2026-11-06

Context: I need to sign in to three accounts from two laptops. IAM users
with access keys are long-lived credentials that can leak, especially in a
public repository.

Options:
- IAM users with access keys: simple; keys never expire unless rotated and
  can be committed by mistake.
- IAM users with console passwords and MFA: no keys for the console, but
  the CLI still needs keys, and each account has its own users.
- IAM Identity Center with SSO: one sign-in with MFA for all accounts,
  short-lived credentials for the CLI, and permission sets assigned per
  account; one more service to set up, and its home Region cannot be
  changed later.

Decision: Use IAM Identity Center in us-east-1 (see ADR-004) with an admin
and a read-only permission set. The CLI uses three profiles named
`management`, `log-archive` and `workload`, created with
`aws configure sso`. No access keys are created for my own use.

Consequences:
- Cost: no additional charge for Identity Center (confirm on the pricing
  page).
- Daily use: sessions expire, so I sign in again when they do; inside the
  dev container (see ADR-005) I use `aws sso login --use-device-code`.
- Scope: this covers my own access only. The GitHub pipeline will use OIDC
  roles instead of keys, and the SOC simulations use temporary lab IAM
  users that are deleted after each session, an exception documented in
  the plan.
- Risk: a mistake in Identity Center could lock me out; each account's
  root user keeps MFA and is the break-glass route.
- Dependency: the home Region is permanent, so I confirmed it before
  enabling the service.
