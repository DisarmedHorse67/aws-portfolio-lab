# ADR-014: Split Terraform into foundation and workload layers

Status: accepted
Date: 2026-11-18
Related: ADR-002 (accounts), ADR-012 (Identity Center).

Context: The repository is public and its pipeline authenticates to AWS
with OIDC roles. The management and log-archive accounts hold the most
sensitive resources (organization trail, SCPs, log bucket), and the
pipeline must not be able to change organization guardrails or its own
permissions.

Options:
- One Terraform root applied only from my laptop: simplest and safest; no
  automated deploys at all.
- One Terraform root applied by the pipeline, with deploy roles in every
  account: fully automated; a compromised workflow could change the
  Organization, the SCPs and the logs.
- Two layers: foundation (management, log-archive, pipeline roles)
  applied from my laptop, workload applied by the pipeline: automation
  where changes are frequent, manual control where they are sensitive.
- A separate repository for foundation: strongest separation; more to
  maintain for one person.

Decision: Use two Terraform layers in one repository: `infrastructure/foundation`
applied by me from the dev container, and `infrastructure/workload` applied by
GitHub Actions through the OIDC roles that foundation creates.

Consequences:
- Blast radius: the pipeline can only act in the workload account, and
  cannot edit its own roles or the SCPs.
- Workflow: pull requests for foundation are reviewed and checked
  (format and validate), but applied manually, so merged code and real
  infrastructure can drift until I apply.
- Permissions: the apply role's policy lives in foundation, so each new
  phase's permissions must be applied from the laptop before the
  pipeline can deploy that phase.
- State: two state keys in the same bucket, two lock files; values shared
  between layers (the role ARNs) are copied by hand into GitHub secrets.
- Setup: more files and one more manual step, documented in
  `docs/runbooks/bootstrap.md`.
